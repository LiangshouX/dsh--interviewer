# 面试准备：产出考点清单

## 这个技能解决什么

一场没有准备的面试是随机提问；一场准备充分的面试是**沿着 JD 的每一条要求，
去验证候选人在简历里声称的那段经历**。所以准备阶段只做一件事：

> 把「JD 要什么」和「这个人有什么」逐条对上，对不上的地方就是考点。

## 输入

- 简历正文（可能已经在 `interview_prepare` 时落盘）
- JD 正文（可能已经在 `interview_prepare` 时落盘，也可能只抓到了链接）

用 `interview_get_context` 一次读全：会话、简历、JD、已有考点清单、统计。

**如果简历或 JD 是空的**：不要自己编。直接告诉用户缺哪一份，并给出两条路：
让用户在插件面板里上传/粘贴，或者直接把内容贴给你。

## 方法

### 第 0 步：先把「这场面试叫什么」写对

**插件不猜元信息。** 标题 / 公司 / 岗位只认你或用户的显式写入；新建的场次
在没人写之前是占位值（`新建公司 2026-11-17` / `新建岗位 2026-11-17`）。

所以开工前先看一眼 `interview_get_context` / `interview_list_sessions` 里的
`title` / `company` / `position`：

- 看得出是哪家公司、什么岗位（JD 标题行、招聘页面）→ 直接写进去；
- 看不出来、或者明显不对 → **问用户一句**，不要从 JD 的「【基础信息】」
  「【职位描述】」这类小标题里抽公司名，也不要把「专家」「工程师」这类词
  当成岗位名硬凑；
- 写回去用同一个工具，**带 `sessionId` 就只更新这一场，不会新建**：

```text
interview_prepare({
  sessionId: "iv-…",
  sessionTitle: "阿里云 · AI 模型与推理产品专家",
  company: "阿里云",
  position: "AI 模型与推理产品专家",
})
```

`interview_save_jd` 只写 JD 正文，**不会**动标题 / 公司 / 岗位——元信息只走这里。

### 第 1 步：把 JD 拆成一条条要求

JD 正文通常已经分了段（插件抓取时会尝试切成 `responsibilities` / `requirements` / `bonus`，
手工粘贴的则按标题切）。逐条编号，每条是一个**可验证的行为要求**，例如：

- 「负责高并发订单系统的稳定性」→ 要求：分布式系统、限流降级、幂等、容量规划
- 「推动服务治理与可观测性建设」→ 要求：链路追踪、指标告警、故障复盘
- 「熟悉 Java 生态，有中间件经验」→ 要求：JVM 调优、中间件（MQ/缓存/注册中心）

**一条 JD 文字不要直接变成一个考点。** 要求是"能力"，考点是"能问出答案的问题"。
一个要求通常对应 1–3 个考点。

### 第 2 步：映射到简历，找**交叉点**

对每个要求，在简历里找：

- **命中**（简历里明确做过）→ 这是**深挖点**，问细节、问取舍、问数据（level: `core` 或 `deep`）
- **部分命中**（沾边但没深入）→ 这是**验证点**，问边界、问如果换个做法（level: `core`）
- **完全没提**（JD 要但简历空白）→ 这是**风险点**，问学习路径或坦诚地说明（level: `core`）

**只从 JD 与简历的交叉点出题。** 简历里毫无体现、JD 也没提的领域不要问——
那是浪费候选人的时间，不是有针对性的面试。

### 第 3 步：分级

| level | 含义 | 数量建议 |
|---|---|---|
| `core` | 必问。直接对应 JD 的硬要求 | 5–8 个 |
| `deep` | 深挖。候选人声称做过、但细节决定真假的地方 | 3–5 个 |
| `bonus` | 加分项。JD 里写了"优先/加分"，或能体现上限 | 0–3 个 |

一份 45 分钟的面试，问 12–16 个考点已经偏多。**宁可少而准。**

### 第 4 步：写清 `why`

每个考点的 `why` 必须能被引用：**JD 的哪一条要求 ↔ 简历的哪一段经历**。
这是面试官（人）能看懂"为什么问这个"的唯一依据，也是后续调整清单时的锚点。

写 `why` 时带上出处，例如：
「JD 要求'负责高并发稳定性'，简历项目 B 写'支撑日订单 800 万' → 问限流与降级怎么做」

### 第 5 步：落盘

调 `interview_save_checklist`，把清单写进去。**不要只在对话里念一遍。**
清单要成为后续面试与报告的共同依据。

### 第 5.5 步：这是不是个"老岗位"？

**同一个岗位第二次面试时，不要从零调研。**

1. 先调 `interview_list_profiles`，看有没有现成的岗位档案。
2. 有 → 调 `interview_apply_profile` 把它的 JD 与考点清单灌进本场会话
   （继承来的考点会被标记为 `inherited`）。
3. 然后**基于继承的清单做增量调研**：保留仍然有效的考点，
   删掉过时的，加上市面上新出现的（比如新的技术栈要求、新的合规要求）。
4. 把增量后的清单用 `interview_save_checklist` 写回本场会话。

**继承不等于照抄。** 档案是基线，不是标准答案。JD 改了、岗位定位变了，
基线就得跟着改——但**改动本身要留痕**，这样复盘时能看出这个岗位在往哪走。

## 反面清单（这些不要做成考点）

- 简历里没有、JD 里没有的"通用八股"
- 纯概念背诵题（"什么是 CAP"）——除非它挂在某个具体决策上
- 涉及薪资、学历、年龄、婚育的问题——不进考点清单
- 只为了凑数的"你还有什么想问的"式伪考点

## 完成标准

清单落盘后，向用户报告三件事：

1. 清单共几项，分级各几项
2. 覆盖了 JD 的哪几条要求，**哪条没覆盖到**（如实说）
3. 建议的面试节奏（几段、每段几分钟）

然后告诉用户可以开始面试了。
